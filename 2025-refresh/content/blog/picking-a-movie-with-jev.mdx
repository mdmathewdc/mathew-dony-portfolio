Choosing what to watch sometimes takes longer than watching it. So I built a small movie picker: type what you feel like watching, and the matching movie posters climb out of a pile. [Check it out here](/apps/jev-movie-picker).

The search behind it isn't keyword matching or a vector database. It runs on a model called Jev.

## Jev?

Jev is [TypeSafe AI](https://typesafe.ai)'s first System One Model, built to make fast, structured decisions. Unlike most LLMs, Jev gives up text entirely: unstructured state goes in, and typed decisions with calibrated probabilities come out.

There are three question types:

- **`noul`**: A yes/no question. The answer is the probability of "yes", from 0 to 1.
- **`choice`**: Pick between named options. You get the top pick plus a probability for every option.
- **`score`**: Rate something against a rubric you define.

Because every answer is a number, the output is always valid and you get a confidence value for free.

## Searching 100 Movies

The catalog is 100 movies, each with a title, year, genres, main cast and a one-line plot summary. The whole catalog is flattened into plain text and passed to Jev as `state`.

The [TypeSafe docs](https://docs.typesafe.ai/concepts/how-to-build-with-system-one) suggest asking many narrow, independent questions together and then composing their answers in code. Questions over the same state run in parallel, so asking more of them doesn't add extra round trips. So the whole search is a single request with three kinds of questions:

```ts
const matchQuestions = Object.fromEntries(
  movies.map((movie) => [
    movie.id,
    noul(`Does "${movie.title}" (${movie.year}) directly satisfy this viewing request: "${query}"?`, {
      true: "This specific movie satisfies the actor, genre, plot, and year constraints",
      false: "This movie is only loosely associated or misses a stated constraint",
    }),
  ]),
);

const response = await client.systemOne({
  state: catalog,
  questions: {
    ...matchQuestions,
    where: choice(`Which movie best matches this viewing request: "${query}"?`, movieCriteria),
    exists: noul(`Does any movie in the catalog reasonably match this viewing request: "${query}"?`, {
      true: "At least one listed movie fits the genre, tone, and any year constraints",
      false: "No listed movie addresses this request",
    }),
  },
});
```

- **`exists`** asks if anything in the catalog fits at all. It's a cheap guard against showing the least-bad movies when nothing really matches.
- **`where`** is a `choice` with every movie ID as an option, so it returns a probability for all 100 movies.
- **One `noul` per movie** asks whether that specific movie satisfies the request. This is the strict check: a movie with a similar vibe but the wrong actor or year won't pass.

## Composing in Code

Once the answers come back, the rest is plain filtering and sorting:

1. If `exists` is below `0.35`, return nothing.
2. Keep every movie whose own `noul` is at least `0.7`.
3. Sort by that score, using the `where` probability as a tiebreaker, and show the top 5.

Each question does one small job, and the code decides how they fit together. No parsing, no retries for malformed JSON and just one model call.

## Thinking in Questions

What I liked most about building with Jev is that it changes how you think about the problem. Instead of prompting a model and hoping for the right shape of answer, you design the questions. "Does anything match?", "Which one fits best?" and "Does this one really fit?" are simple questions, and asked together in one request they make a decent search engine for a small catalog.

It's not a replacement for a proper search index once you have millions of items. But for small, well-described sets like a product catalog, support ticket routing or a list of movies, it's a surprisingly clean way to get a model to make decisions.
